# ブログ「現場ノート」の設計（2026-11-14）

MiraGeru の LP（https://lp.mirageru.com、このリポジトリ）に、店舗オーナー向けのブログ「現場ノート」を足し、記事づくりと月1回のSEOの見直しを Claude Code のコマンドで回せるようにする。

関連：土台の修正は公開済み（`2026-11-14-seo-foundation-design.md`、コミット `52f9100`）。デザインの見本は `.superpowers/brainstorm/62549-1794625806/content/design-v2.html`（git 管理外。必要な値はこの文書に写してある）。

---

## 1. なぜ（意図）

- オーナー（片山 真介、個人事業主・副業）の事業は「業務の標準化とリーダー育成の伴走支援」。今の課題は集客。
- 記事を読んだ**店舗オーナーから問い合わせ（LINEで50分の無料相談）をもらう**ことがいちばんのゴール。あわせて検索からの流入と認知を LP に積み上げる。
- 材料は、オーナーが毎日 X（@coach_katayama）で発信している言語化。X では認知を広げるために主語を「上司・部下・ビジネスパーソン」に広げているだけで、本来届けたいのは店舗ビジネスの人。

## 2. ゴール・やらないこと・失敗とみなすこと

**ゴール**
- `lp.mirageru.com/note` に記事の一覧、`/note/<slug>` に記事が出る。見た目は見本どおり
- 週1本のペースで、オーナーの手間は「質問に5〜10分答える＋確認」だけで記事が出せる
- 記事の最後と途中、スマホの下から LINE の無料相談に進める。その押された数を GA4 で数えられる
- 月1回、Search Console とキーワードプランナーの CSV から、次にやることが出る

**やらないこと**
- note・WordPress など外部のブログサービス
- Claude API の従量課金、有料の SEO ツール
- Google の API 連携（Search Console・GA4）。月1回の CSV で回す
- 古いサイト（blog.mirageru.com・support.mirageru.com・excel-resolution.mirageru.com）には触らない（オーナーの判断：残す）
- LP のトップ以外のセクションの大きな作り直し（下の 5.4 にある範囲だけ直す）

**失敗とみなすこと**
- オーナーの確認なしに本番（main）へ記事や変更が出る
- 出どころの確かめていない数字・引用が記事に入る。本や研究の文章の長い引用
- 他人の X の投稿・画像を材料にする（使うのは自分の投稿だけ）
- 記事が「どこにでもある一般論」になり、片山さんの体験が入っていない
- ページの表示が遅くなる、LP の今の見た目が壊れる

## 4. 作り方の比較（Approaches）

**記事の置き場所**
- A（採用）LP の中に置く：検索の評価が LP に貯まる、見た目と LINE ボタンを自由にそろえられる、費用ゼロ
- B note など外部ブログ：すぐ始められるが、評価が外に貯まり、自動で投稿できない
- C WordPress 等の新しいサービス：月額と管理が増えるだけで A より良い点がない

**SEO の数字の受け渡し**
- A（採用）オーナーが月1回 CSV を書き出す：設定不要・安全、手間は月5〜10分
- B Google API 連携：自動だが Google Cloud の設定が重い。記事が20本を超えたら再検討
- C Claude がブラウザで画面を見る：毎回ログインが要り、広告アカウントに入ることになるので使わない

**X の画像の読み方**
- A（採用）Grok の X Search（`mcp__hermes__x_search`）に自分の投稿を読ませる：X プレミアムの範囲、2026-11-14 に1件試して画像の会話まで全文読めた
- B ブラウザで X を開く：X の規約（自動の読み取り）とログインの問題があるので使わない

**記事の確認のしかた**
- A（採用）作業用のブランチを GitHub に送り、Vercel の確認用 URL（Preview）をオーナーがスマホで見る：本番と同じ見た目で確かめられる
- B 手元のサーバーだけで確認：オーナーがこの Mac の前にいないと見られない

## 5. 作るもの

### 5.1 デザインの決まり（全ページ共通）

| 役割 | 色 | 使う所 |
|---|---|---|
| 青緑（今の LP） | `#169db2` | 広い面、大きな見出しの強調、方眼の線 |
| 濃い青緑（新規） | `#0e7c8c` | 青緑のボタン、小さな文字、リンク（白文字で 4.9:1） |
| うすい青緑（新規） | `#e3f4f6` | 要点・相談の案内の背景、チップ |
| 紺（今の LP） | `#0F172A` | 本文の文字、サムネイル・見出し帯の地 |
| 背景（今の LP） | `#F8FAFC` | ページの地 |
| LINE の緑 | `#06c755` | LINE ボタンだけ |

- `#169db2` の上に白い小さな文字を置かない（3.2:1 で基準未満）
- 方眼：紺の地に `rgba(22,157,178,.18)` の 1px の線、14px 間隔。通し番号は等幅の文字で `#6fd6e6`
- 文字は今の LP と同じ（Noto Sans JP・Inter）
- LINE ボタンのラベルは「LINEで無料相談する」、補足は「50分・オンライン・売り込みはしません」

### 5.2 記事の一覧 `/note`
- 見出し帯：紺×方眼、「GENBA NOTE」「現場ノート」「お店の標準化と人づくりを、元店長の目線で。」
- テーマで絞りこみ：すべて／スタッフ育成／マニュアル／店長の仕事／作業割当（テーマは記事のデータから作る。件数ゼロのテーマは出さない）
- 新しい順。いちばん新しい1本は大きなカード（サムネイル＋題名＋日付・読む時間＋手順の数）、2本目以降は小さな行
- ヘッダーは LP と同じ（ロゴの横に「現場ノート」）。ヘッダーの「無料相談」は濃い青緑

### 5.3 記事のページ `/note/<slug>`
上から順に：
1. 見出し帯（紺×方眼）：「現場ノート No.○○ ・ テーマ」、題名、副題
2. 書いた人：顔写真（`public/images/profile.png`）、「片山 真介（元ニトリ店長・15年）」、日付・読む時間
3. この記事の要点：番号つき手順 3〜5
4. 目次（見出しへ飛べる）
5. チェックリスト → 「2つ以上あてはまるなら、無料相談で一緒に整理できます →」の軽い案内
6. 本文：見出し・手順・チェックリスト・ビフォーアフターの表や図。ニトリ時代の体験を1つ以上
7. 出どころ（参考にした本・研究・公的資料のリスト、リンクつき）
8. 最後の相談の案内：うすい青緑の囲み、題名に合わせた一言＋「50分の無料相談で、最初の一歩を一緒に決めます」＋LINE ボタン
9. 関連記事 2〜3本（同じテーマを優先）
- スマホでは、読んでいる間ずっと画面の下に LINE ボタン（補足「50分・オンライン」）
- 図解は記事のデータの中で書けるもの（表・番号つき手順・チェックリスト・対比の2列・フロー）を部品として用意する。画像を描く必要はない

### 5.4 LP のトップ（見本①）
- 最初の画面：「スタッフ3〜20名の店舗オーナーへ」、見出し「『自分がいないと回らない』を、仕組みで卒業する。」、説明「業務の標準化とリーダー育成を、ニトリ15年の元店長が、あなたのお店で一緒に進めます。」、顔写真と経歴（ニトリ15年・店長3店舗・120名のマネジメント）、LINE ボタン、「50分・オンライン・売り込みはしません」
- 今のヒーロー右側の紺の「なぜ ミラゲル か」パネルは、写真と経歴のブロックに置きかえる（Claudeの判断）。パネルの3つの点のうち、経歴（ニトリ15年…）は写真のブロックへ、残りの2つ（御社専用の仕組みを一緒につくる／定着するまで動ききる）は写真のブロックの下に短い2行で残す
- その下に「現場ノート 新着」2〜3本と「すべて見る →」。記事がまだない間は出さない
- ヘッダーの「無料相談」とボタンの色を 5.1 の決まりに合わせる。ヘッダーのページ内リンク（`#pain` など）は、記事のページからでも LP の該当箇所に飛べるようにする
- スマホの下の LINE ボタンは LP にも出す
- 今の「お悩み」以下のセクションの文章は変えない

### 5.5 SEO の部品
- 各記事：`title`（ねらう言葉を入れる）・`description`・canonical・OGP・Article と Person（片山 真介、`SITE_URL/#person`）の構造化データ。BreadcrumbList（トップ › 現場ノート › 記事）
- `/note` にも title・description・canonical
- サイトマップに `/note` と全記事を自動で載せる（記事の日付を lastModified に）
- 住所は `src/lib/constants.ts` の `SITE_URL` から作る
- サムネイル（OGP 画像）は題名から自動で作る：紺×方眼、「現場ノート No.○○ ・ テーマ」、題名、副題、「ミラゲル」のロゴ。1200×630。記事ごとに画像ファイルを用意しない

### 5.6 計測
- GA4（`G-BDNEB2NYYD`、layout.tsx に入っている）に、LINE ボタンのクリックをイベントで送る。イベント名 `line_click`、パラメータに置き場所（`hero`・`header`・`sticky`・`article_mid`・`article_end`・`cta_section` など）と、記事なら slug
- 計測が広告ブロック等で動かなくても、ボタンの移動は止めない

### 5.7 記事のデータ
- 1記事1ファイル、リポジトリの中（`content/note/` を想定）。オーナーが読める形（Markdown 系）
- 記事ごとに持つ情報：通し番号、slug、題名、副題、description、ねらう言葉、テーマ、日付、更新日、読む時間、要点（手順）、チェックリスト、最後の案内の一言、出どころ、元にした X の投稿の URL、下書き／公開の別
- 下書きの記事は本番に出さない（一覧・サイトマップ・直接の住所のどれでも出ない）

### 5.8 コマンド（`mirageru-company/.claude/commands/`）
オーナーは `~/claude/mirageru-company` で Claude Code を使う。コマンドはそこに置き、LP のリポジトリ（`~/claude/web-app/mirageru-lp`）を操作する。どちらのコマンドも、オーナーに話すときは「やさしい日本語で、短く」。

**`/note-article`（週1回）**
1. 候補の一覧（`mirageru-company/.company/marketing/content-plan/note-candidates.md`。今日の10本（`note-article-candidates-2026-11-14.html`）と、4〜5月の note の下書き（同じフォルダの `note-draft-*.md`、オーナーOK 2026-11-14）から始める。note に公開済みの `note-draft-b01-hitori.md` は同じ文章を2か所に出さないよう、書き直す前提で入れる。下書きがある候補は、質問で下書きにない場面だけを聞く。状態：候補→作成中→確認待ち→公開）から次の1本を提案。オーナーが決める（引数でテーマを指定してもよい）
2. 材料：𝕏分析シート（ID `1tNY_wl-frY3tjxhbVwocJYhHAagUO5qQTVS5dPuhx3M`、`_集計ポスト`、読むだけ）で元の投稿と関連する投稿を探す。画像の投稿は `mcp__hermes__x_search`（`allowed_x_handles: ["coach_katayama"]`、`enable_image_understanding: true`、投稿日の前後で期間をしぼる）で中身を読む。1記事あたり Grok の呼び出しは3回まで
   - シートが読めないとき（Claudeの判断）：黙って別の方法に切りかえない。止めて、オーナーに「Google スプレッドシートのつなぎ直し」をお願いする。つなぎ直せないときは、オーナーが元の投稿の URL を貼る→その投稿だけ Grok で読む、で続けてよいかを聞く
3. 裏づけ：外の考え方・データを1〜2個、Web で出どころを確かめる。片山さんの考えと「同じ所」と「ちがう所」を分ける。長い引用はしない
4. 質問：ニトリ時代の具体的な場面を2〜3個、チャットで聞く（5〜10分）。答えは記事のメモとして残す
5. ねらう言葉：Google の検索候補で確かめる。月1回の CSV（キーワードプランナー）に回数があれば使う
6. 下書き：5.3 の形で書く。主語は店長・スタッフ・オーナー
7. 確認：作業用ブランチを GitHub に送り、Vercel の確認用 URL をオーナーに渡す。直しがあれば直す
8. オーナーの OK のあと、main に入れて送る → 本番に出たことを確かめる → 候補の一覧を「公開」に
- GitHub への送信は git の設定を変えず、そのときだけ `gh` の認証を使う（`git -c credential.helper= -c 'credential.helper=!gh auth git-credential' push https://github.com/katashin/mirageru-lp.git <branch>`。このMacの SSH 鍵は使えない）
- 公開前に、テストとビルドを通す

**`/seo-check`（月1回）**
1. 書き出す CSV と手順をオーナーに案内：Search Console（ドメインプロパティ `mirageru.com`、検索パフォーマンス、`lp.mirageru.com` に絞る、直近28日、クエリとページ）と、キーワードプランナー（Claude が出した言葉のリストの月間検索数）
2. 置き場所：`mirageru-company/.company/marketing/seo-data/YYYY-MM/`
3. 見直し案：11〜20位の記事の手直し、表示が多くクリックが少ない記事の題名の直し、新しく出てきた言葉と次の記事の候補。候補の一覧に足す
4. 結果を `mirageru-company/.company/marketing/seo-pdca-log.md` に追記（タイムスタンプつき）。GA4 の `line_click` の数もオーナーに見てもらい記録する

## 6. 制約
- Next.js 16（App Router）・React 19・Tailwind 4・framer-motion。Vercel（GitHub の main に送ると自動で本番公開。Vercel のプロジェクトが2つ `mirageru-lp`・`mirageru-lp-bs4y` あり、どちらにも出る）
- 既存のテスト（Jest 44件）とビルドを壊さない。新しい部品にもテストを足す
- 公開中のページを書き換える前には必ずオーナーの確認を取る
- `next.config.ts` が `typescript.ignoreBuildErrors: true` になっている（型エラーでもビルドが通る）。新しいコードは型エラーを出さないこと

## 7. 作る人に任せること
- 記事データの細かい形式（frontmatter の項目名、MDX にするかどうか）と、本文の部品の作り方
- 記事を読むライブラリの選択（入れすぎない。表示を遅くしない）
- サムネイルの作り方の技術（Next.js の OGP 画像の仕組みなど）
- コマンドのファイルの書き方の細部（今の `/x-trend` の書き方に合わせる）
- 最初の1本の記事は、仕組みができたあと `/note-article` で作る（仕組みの確認を兼ねる）。それまでは一覧・新着は空でも壊れないこと
